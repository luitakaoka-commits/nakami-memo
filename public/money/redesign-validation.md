# お金管理の再設計：計算の検証メモ

このファイルと `redesign-readiness.js` / `redesign-card-reconciliation.js` は、再設計の**検証用の試作**です。現在の画面・Firestore・Apps Script・本番計算には接続していません。テストは架空の金額・口座・カードのみを使います。

## 判定の前提

- 確認済みの口座残高から始め、将来の出金を引落口座ごと・日付順に評価する。
- 「安全」は、請求額が確定し、残高が確認でき、未入金の給与・振替に依存しない場合だけ。未確定や不明な情報がある場合は「要確認」。予定収入が入っても不足するときは「不足見込み」。
- 対象期間の口座・請求・未照合候補が網羅されている根拠も必要。`coverageVerified` が未指定または偽なら、判明している不足は警告し、それ以外は要確認とする。日々の手動確認を前提とせず、自動取り込みの状態などから根拠を管理する仕組みは未実装。
- 予定収入・振替は将来の見込みには入るが、実行前に確実な資金とはみなさない。同日中の入金・振替が引落より前に完了する保証はないため、同日の引落判定後に反映する。
- 試作は振替元の予定残高が不足する場合、その振替先に架空の入金を作らずエラーを返す。本番接続時はエラーを握りつぶさず「振替の資金・入金順序を要確認」と表示する必要がある。
- 各予定額は最低限確認できた額と、未照合の追加可能額を分ける。追加の可能性を含めて支払い余力が不確かなときは安全と表示しない。
- 確認済み残高は**開始日時点で確定済みの取引が反映された額**とし、過去の未処理予定がある場合は自動的に引き直さず「要確認」とする。
- 各予定は `status: planned`（未実行）または `settled`（実行済み）を必須とする。実行済みの取引は開始残高に含まれるため再計上しない。`amountConfirmed` は請求額の確定状態であり、`status` とは別。未来日の実行済みは整合性エラー。
- 次回のカード引落と、その後の水道代等を含む期間全体の状態を分ける。固定の15,000円は強制しない。

## カード累計とメールの照合

- 同じカード・請求期間の確定請求額、途中の累計、個別利用を混ぜない。各明細の「累計に含まれる／含まれない／不明」は、独立した照合で裏付けられた結果を渡す。
- 累計に含まれないと確認できた利用だけを加算し、不明分は別途追加の可能性として示す。確定請求額は勝手に加減しない。
- 累計の確認日時が不明、途中累計の最新利用日時が不明、最新利用日時が確認日時より後、または内訳の合計が累計額を超える場合は要確認とする。内部APIの `confirmed` はこれらの確認も通った場合だけ真とし、カード会社の表示上の確定状態は `sourceConfirmed` と分ける。
- 累計を確認した後の利用が、その累計に含まれるという矛盾は要確認。途中累計なら追加の可能性を残し、確定請求額は変更せず矛盾を知らせる。日時が前であることだけから包含を確定しない。
- メールはカード識別・金額・**実際の利用日時**の根拠とメールIDが必要。受信時刻は利用時刻の代わりにはならない。同じメールIDの再取得と、別メールだが同じ利用かもしれない事象を区別する。
- 作業用コードでは本文の「利用日時」を日付・時刻・時間帯の根拠に分ける。日本時間の明示があり、利用日を変更していない場合のみ取引時刻に使う。時間帯不明・時刻の矛盾・ラベルが複数のときは時刻を確定しない。旧候補と旧取引は自動修正しない。新しいFirestoreルールとApps Scriptは未公開で、実機検証は未完了。
- 明細の取得元はメールまたは手入力として明示し、取得元が不明なデータは受け付けない。手入力でも日時などの根拠が必要。
- 別メールIDというだけでは別取引と断定しない。重複判定が未実施・曖昧なもの、取消や返金、証拠が欠けるものは要確認。
- 同一メールの再取得でも抽出金額・利用時刻・種別が食い違う場合は単純に捨てず、未確定の追加可能額に残す。確定請求額自体は勝手に変えず矛盾を示す。

## 検証範囲と未完了

`node public/money/tests/redesign-core.test.js` は、口座別・同日複数請求・給料・振替・水道代・予定の重複・不明額・カード累計とメールの例外を検証する。複数の架空金額の組合せは独立した手計算と比較する。既存の `npm test` にも追加した。

Firestoreルールの候補に関する9項目を、`demo-kurashi` のローカルエミュレーターと架空データで検証済み。新旧の候補を本人が書けること、不正な時刻・時間帯・出所・未知の項目を拒否すること、本人以外と未ログインを拒否することを確認。`public/money/tests/rules-emulator.test.js` は `FIRESTORE_EMULATOR_HOST=127.0.0.1:8487` を明示した場合にのみ実行でき、接続先は固定のデモプロジェクト。自動テストだけではデプロイ済みルールやApps Scriptとの接続、実機の権限を保証しない。

共有の検査では同居人が本人の家計・メール候補を読めず、共有在庫を読めることを確認した。一方、共有在庫に購入金額が入っていれば同居人に読めることも確認した。新規の共有在庫と個人在庫から家を作るコピーでは購入金額を除く修正を追加し、ルールでも共有在庫への新規追加・金額変更を拒否する。既存の金額を変えずに他の項目を編集することと、金額を削除することは許す。架空データのエミュレーター検証は19件すべて成功。**すでに共有済みの在庫は変更していない**ため、既存データの安全なバックアップ・移行が必要。レシート参照や家計スペースIDは連携のため共有される点にも注意。既存の古いアプリは購入金額つきの共有在庫を新規作成できなくなるため、公開するときはプレビューと更新済みの各アプリを確認した後にルールを公開する。GASの新しい時刻フィールドはルール公開後にスクリプトを更新する。実機確認は未完了。

`redesign-migration-check.js` は架空の JSON データによる比較の試作で、家計本体とメール候補・レシート・明細・別名辞書の欠落や内容の変化を検出する。取得完了の印は呼び出し側から与える前提で、その真偽は検証できない。Firestore固有の値、取得漏れ、バックアップの作成、実際の復元や認証は未対応。これを完全なバックアップ機能とみなさない。

`redesign-backup-read.js` はFirestore RESTの応答を受け取る読取専用の試作。親文書と4種類のサブコレクションの全ページへ同じ `readTime` を指定し、文書名、重複、ページの繰り返し、取得失敗を検査する。Firestoreの値はRESTの型付きJSONのまま保持する。[Firestore get](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/get) と [list](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/list) の仕様を参照。サーバーが許す読み取り時刻と認証の取得、実通信、ファイル保存、復元、権限、ネットワーク障害、下位の別アプリのデータはまだ未検証。対応した4種類以外や別のアプリを含む完全バックアップではない。

`redesign-recurring.js` は明示された初回日と間隔から隔月などの予定を生成する試作。月末の調整と同じ定期予定・同じ日付の登録済み取引との重複を検査する。金額が未入力なら0円の未確定として扱い、入力済みでも各回の実際の請求額が確定したとはみなさない。水道代の実際の引落日・祝日調整・金額は自動判定しない。既存の定期予定をこの形式へ移行する処理は未実装。

`redesign-legacy-adapter.js` は既存の架空の家計データから、新判定で読める試験用入力を作る。残高・請求・全データの網羅を確認済みとはみなさず、旧カードの請求総額と内訳の重なりは追加の可能性として残す。複数の総額、引落日やカード口座の矛盾はエラーにする。条件を満たす旧形式の毎月の定期予定は、既存の展開処理を使い、実取引との重複も検査する。適用できない定期予定や計算除外された取引は未反映の注意を返す。給与記録のある月・削除した月はシフトによる見込みを足さず、給与の入金口座を特定できない場合は入金を作らず注意を返す。この形式の金額は未完成の参考値で、実データへ適用・画面表示・保存する機能ではない。旧形式の全取引種別、実データの個別の確認、隔月予定への移行・メール候補の照合は未完了。

旧データで総額がなく明細だけの場合も、メール間の重複照合や利用日時の根拠を引き継げないため、全明細を追加の可能性として扱い確定額にはしない。これは慎重な上限であり、実際の請求額ではない。

現行の設定画面のJSON書き出しは `state` のみで、上記のサブコレクションは入らない。さらに現行画面の読み込み処理は口座・カード・取引の未知の項目を捨てるため、新しい項目を同じ場所に追加して旧画面で保存すると消える危険がある。複数端末からの `state` 保存も競合対策が必要。自動メール取込は現在 `importCandidates` に保存されるので、メール取込自体が `state` の取引配列を書き換えると断定しない。

**未完了：** 実際のデータから上記入力を正しく生成するアダプター、カード会社ごとの実利用時刻とカード識別、メール間の重複判定、累計の根拠管理、請求確定と引落完了の保存、CSV照合、隔月の水道代の予定生成、残高照合、移行・復元、同期の競合制御、３アプリ間の実データ権限検証、UIと実機確認。試作関数は入力の正しさを独立して保証しない。特に `coverageVerified`・`balanceVerified`・`amountConfirmed`・`evidenceComplete`・`duplicateCheck`・`inclusion` は根拠を持って決める必要があり、現在の取込結果から自動的に真にしてはいけない。

資料の入出金表との直接比較は別途、利用者の実データを外部へ出さない環境で行う。過去の残高を現在値と決めつけない。
